The connector wizard takes a pre-registered OAuth client's ID and secret in "Each person signs in with their own account" mode; muster stores them in a Secret bound to the connector. An edit shows the client as stored, with Replace, and asks for it again when the issuer or an endpoint changes; choosing "Existing Secret" names a Secret instead. Both choices say they are about a Kubernetes Secret of type Opaque. The existing Secret's name, namespace and data keys are checked as Kubernetes names when the person leaves the field and again on save, with the error under the field; left all empty, Existing Secret is no client, as New Secret is. The key fields show their defaults, `client-id` and `client-secret`, as placeholders. Switching between the two keeps what was typed on either side, except a typed client secret. On a muster whose create and update take no `clientCredentials`, New Secret offers no client fields and says to name an existing Secret instead. In the Advanced settings the issuer comes first, then the endpoints and scopes, and scopes are no longer greyed out before an issuer is set. The values go only into muster's create or update call: not into validation, the form's saved state, analytics or errors.

muster-backend answers a refusal of muster's connector writes (`core_mcpserver_create`, `_update`, `_validate`) on `/call` with 422 instead of 500, so it no longer reaches Sentry: a permission muster names, an invalid definition, a name taken, muster's own rules or an admission policy's denial. muster's own failures keep their 500.
